# 项目演变史

## 这份文档要解决什么问题

学习者面对一个已经拆好的 milestone 时，往往知道“要写哪些函数”，却不知道：

- 项目最初要解决什么问题；
- 当前阶段为什么会出现；
- 前一个版本有什么限制；
- 当前设计会如何推动下一个版本；
- 最终的多个源文件和数据层是怎样逐步长出来的。

因此，课程不能只给出任务清单，还需要展示一条“问题 → 压力 → 设计变化 → 新限制”的演变链。

这条路线类似于一个 Web 项目的成长：先有静态页面，后来需要交互，于是引入前端状态管理；再后来需要服务端逻辑，于是出现 API 和后端；最后因为数据需要长期保存，引入数据库。

本项目没有 React、Next.js、FastAPI 或数据库，但它同样可以用设计压力解释自己的成长过程。

## 项目最终要解决什么问题

这是一个命令行图书管理系统，最终需要支持：

- 添加图书；
- 查看图书；
- 修改图书；
- 删除图书；
- 搜索图书；
- 借书和还书；
- 保存并恢复数据。

最终系统可以抽象为三层：

```text
main.c
用户界面层：菜单、输入、提示
        ↓
business.c
业务逻辑层：添加、修改、删除、搜索、借还
        ↓
data_mgr.c
数据层：结构体、数组、文件读写、查找工具
```

数据流大致是：

```text
用户
 ↓
菜单
 ↓
业务函数
 ↓
内存数组
 ↓
文本文件
```

但这个结构不是一开始就应该出现的。它是多个问题连续出现后，逐步形成的结果。

## 演变总览

| 阶段 | 系统状态 | 当前问题 | 因此引入 |
|---|---|---|---|
| 0 | 写死几本书并打印 | 用户不能操作 | 菜单和用户输入 |
| M01 | 菜单 + 内存数组 | 能添加，但只能临时保存 | `Book`、静态数组、`bookCount` |
| M02 | 内存中的增删改查 | 重复 ID、无法修改和删除 | CRUD 函数、唯一性检查、数组前移 |
| M03 | 图书数据可被管理 | 程序重启后数据消失 | 文本文件持久化 |
| M04 | 图书数据可以保存 | 图书变多后难以查找 | ID、书名、作者搜索 |
| M05 | 可以管理书籍 | 总库存和当前可借数量不同 | `quantity`、`available`、借阅记录 |
| M06 | 主要功能已经完整 | 乱输入、缺文件、坏数据会破坏系统 | 输入校验和健壮性处理 |
| 最终形态 | 一个完整的 CLI 系统 | 功能越来越多，职责容易混在一起 | UI、业务、数据分层 |

## 阶段 0：从静态演示开始

最开始可能只有几条输出语句：

```c
printf("C Programming\n");
printf("The Art of Computer Programming\n");
```

此时它还不是图书管理系统，只是一个展示数据的 C 程序。

### 当前能力

- 程序可以运行；
- 程序可以显示书籍信息。

### 当前限制

- 图书写死在源代码中；
- 用户不能添加自己的书；
- 程序没有状态，也没有操作流程。

### 下一步压力

如果用户不能输入和管理数据，这个程序就没有实际的管理价值。

## 阶段 M01：从静态演示变成可操作程序

M01 的目标不是做完整系统，而是让用户第一次能够真正操作程序：

```text
用户选择 1：添加一本书
用户选择 2：列出所有书
用户选择 0：退出
```

为此引入：

```c
struct Book {
    char id[20];
    char title[100];
    char author[100];
    int quantity;
    int available;
};

struct Book books[1000];
int bookCount = 0;
```

数据流变成：

```text
用户输入
   ↓
Book 结构体
   ↓
books[]
   ↓
listAllBooks()
```

### M01 解决的问题

- 用户可以输入图书；
- 程序可以暂时保存多本书；
- 用户可以查看当前图书列表；
- 重复运行菜单成为可能。

### M01 刻意留下的问题

- 数据只保存在内存中；
- 程序关闭后数据会消失；
- 还不能修改和删除；
- 还不能搜索和借还。

程序退出后数据消失不是 M01 的 bug，而是下一阶段设计压力的来源。

## 阶段 M02：从“能添加”变成“能管理”

M01 使用一段时间后，用户会提出新的需求：

- ID 重复了怎么办？
- 书名写错了怎么办？
- 不需要的书怎么删除？
- 能不能找到指定的书？

于是系统增加：

```text
findBookIndex()
updateBook()
deleteBook()
```

这里的重点仍然是内存数组，并没有引入文件或数据库。

### 删除为什么要前移

静态数组中不能简单地“删除一个位置”。例如：

```text
A B C D
```

删除 B 后，需要把后面的元素左移：

```text
A C D
```

因此使用：

```text
books[i] = books[i + 1]
bookCount--
```

### M02 解决的问题

- ID 可以保持唯一；
- 数据可以修改；
- 数据可以删除；
- 数组仍然保持连续和可遍历。

### M02 刻意留下的问题

即使 CRUD 完整，程序重启后所有数据仍然会丢失。

## 阶段 M03：从“能管理”变成“能保存”

M02 之后，程序已经像一个小型管理系统，但它有一个明显缺陷：

```text
今天添加了 100 本书
关闭程序
明天重新打开
全部没了
```

这个问题推动持久化设计。

第一种简单方案是使用人类可读的文本文件：

```text
内存数组 ←→ books.txt
```

启动时：

```text
books.txt → loadData() → books[]
```

修改后：

```text
books[] → saveData() → books.txt
```

这时才自然需要：

- `fopen`；
- `fprintf`；
- `fgets`；
- `strtok`；
- `atoi`。

因此，文件读写不是项目的起点，而是“内存数据会丢失”之后的解决方案。

### M03 的设计选择

使用管道符分隔的文本：

```text
B001|C Programming|Alice|3|3
```

它的优点是：

- 不需要数据库；
- 不需要第三方库；
- 人可以直接查看文件；
- 对当前规模来说足够简单。

### M03 刻意留下的问题

- 图书多时，全部列出会很长；
- 字段中不能自然包含 `|`；
- 文件格式还不够健壮；
- 搜索仍然需要人工浏览。

## 阶段 M04：从“能保存”变成“能找到”

当数据量增加后，用户不想每次都查看全部图书再肉眼寻找目标。

于是增加：

- 按 ID 搜索；
- 按书名搜索；
- 按作者搜索。

这不是因为数组不能工作，而是因为原来的交互方式在数据量变大后效率太低。

这一步仍然可以使用线性遍历，不需要马上引入复杂的数据结构或搜索引擎。

## 阶段 M05：从“管理书籍”变成“管理借阅业务”

单纯的图书管理只需要一个数量，但借阅会带来新的业务问题：

```text
图书总共有 3 本
借出去 1 本
当前只能再借 2 本
```

因此需要区分：

```text
quantity   总拥有量
available  当前可借数量
```

同时需要新的记录：

```text
BorrowRecord
```

借书时：

```text
available--
创建借阅记录
```

还书时：

```text
available++
标记借阅记录已归还
```

此时项目已经从“保存一组书”发展成“维护一组业务状态”。

## 阶段 M06：从“能用”变成“可靠”

主要功能完成后，真实用户会输入各种意外内容：

- 数量输入 `abc`；
- ID 为空；
- 文件不存在；
- 文件字段数量不完整；
- 库存超过容量；
- 还没有借出却尝试归还；
- 重复借阅同一本书。

于是系统需要：

- 更严格的输入校验；
- 容量上限检查；
- 缺失文件处理；
- 损坏记录处理；
- 库存不变量保护；
- 更明确的更新语义。

这一步不是增加新的主要功能，而是让已有功能在现实输入下仍然可信。

## 最终架构是如何长出来的

最初可以把所有代码写在一个 `main.c` 中，因为功能很少：

```text
main.c
菜单 + 数据 + 添加 + 列表
```

随着功能增加，职责开始混在一起：

```text
main.c
菜单 + 输入 + 添加 + 删除 + 借书 + 文件读写 + 查找
```

于是自然产生拆分需求：

```text
main.c
只负责菜单、输入和调用

business.c
负责图书业务与借还规则

data_mgr.c
负责结构体、数组、文件和工具函数
```

这不是一开始就需要设计的“完美架构”，而是代码规模扩大后，为了降低理解和修改成本而形成的分层。

## 与 Web 项目成长的类比

可以用下面的方式理解两种项目的共同模式：

| Web 项目 | 图书管理项目 |
|---|---|
| 静态 HTML | 写死几本书并打印 |
| 表单和交互 | CLI 菜单和用户输入 |
| 前端状态 | C 内存数组和 `bookCount` |
| CRUD 页面 | 添加、修改、删除、查看 |
| 服务端持久化 | `loadData/saveData` |
| API/业务逻辑 | `business.c` 中的业务函数 |
| 数据库 | 当前项目未来可替换文本文件的存储层 |
| 输入校验和错误处理 | M06 健壮性 |

但这个类比不是说两者技术上完全相同。它们相同的是演变规律：

```text
最小功能
  ↓
用户提出新需求
  ↓
旧结构产生压力
  ↓
引入新的抽象或存储方式
  ↓
形成更完整的系统
```

## 对课程 skill 的改进建议

课程不应只按下面的方式引导：

```text
请实现 addBook()
请实现 listAllBooks()
请完成验收
```

而应该在每个 milestone 开始前先交代四件事：

1. 上一个版本已经能做什么；
2. 用户现在遇到了什么具体问题；
3. 为什么当前技术或结构能解决这个问题；
4. 当前方案会留下什么新的限制。

每个阶段可以固定使用以下模板：

```text
## 当前版本

## 上一版本解决了什么

## 用户遇到的新问题

## 本阶段引入什么

## 本阶段解决什么

## 暂时不解决什么

## 下一阶段为什么会出现
```

这样学习者面对的就不再是孤立任务，而是一条有因果关系的项目成长路线。

## 需要特别说明的教学事实

`M01 → M06` 是为了教学而设计的演变路线，不一定等同于原项目真实的提交历史。

它的价值不在于复原作者当年每一步具体做了什么，而在于让学习者看到：

```text
为什么先有内存数组
为什么后来需要文件
为什么功能变多后要分层
为什么数据库或更复杂框架不应该一开始就引入
```

最终目标不是背下某个项目的代码，而是学会根据实际压力逐步增加复杂度。
