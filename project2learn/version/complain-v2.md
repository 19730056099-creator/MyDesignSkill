# Project2Learn v2 版本说明

## 第一版的痛点

v1 已经能生成准备度模型、前置补给、路线图和压力驱动的里程碑，但学习者仍可能只看到一组结构化任务：

```text
实现某个函数 → 运行验收 → 进入下一阶段
```

主要问题是：

1. **阶段之间的因果关系不够显式**：里程碑有“设计压力”和“下一项压力”，却没有强制交代上一版本已经提供的价值。
2. **学习者知道写什么，不一定知道为什么现在写**：任务、函数和验收可能完整，但设计变化仍像课程作者预先安排的答案。
3. **最终架构的形成过程不清楚**：架构文档解释成熟组件如何协作，却没有集中展示这些组件分别在什么压力下才有必要出现。
4. **路线图承担了两种职责**：它既要说明构建顺序，又隐含解释阶段动机，导致“做什么”和“为什么”容易混在一起。
5. **教学路线可能被误读为真实历史**：虽然 v1 已要求标注教学推断，但缺少一个专门产物持续声明演变路线不等于作者提交历史。
6. **双语和并行生成缺少演变链硬契约**：生成器可以写出配对里程碑，却未强制两种语言共享同一套阶段因果字段。

## 第二版改进了什么

### 1. 新增双语 `project-evolution.md`

每个 schema-v2 课程必须生成：

```text
course/zh-CN/project-evolution.md
course/en/project-evolution.md
```

它集中说明：

- 项目最终解决的问题与成熟能力；
- 不复制最终架构的最小可用起点；
- 整体演变总览；
- 每个阶段的因果链；
- 最终架构如何随压力逐步形成；
- 教学重建路线与真实提交历史的区别；
- 支撑这些解释的证据台账。

### 2. 里程碑改为显式因果模板

v2 的每个新里程碑必须回答：

```text
当前版本
→ 上一版本解决了什么
→ 用户遇到的新问题
→ 本阶段引入什么
→ 本阶段解决什么
→ 暂时不解决什么
→ 下一阶段为什么会出现
```

任务、验收、五级提示和源码桥接继续保留。这样阶段不再是孤立功能清单。

### 3. 增加语言中立的演变模型

在写中英文课程前，先建立共享模型：

- `mature_problem`
- `mature_capabilities`
- `minimum_viable_start`
- `stages[].current_version`
- `stages[].previous_value`
- `stages[].new_problem`
- `stages[].introduced_change`
- `stages[].resolved_pressure`
- `stages[].deferred_limit`
- `stages[].next_pressure`
- `architecture_growth`
- `route_disclaimer`

中英文演变文档和里程碑都从这套模型渲染，避免由一种语言松散翻译另一种语言。

### 4. 增加因果连续性规则

- M01 必须从最小可用起点出发；
- 后续阶段的“当前版本”必须对应上一阶段产出的系统；
- 当前阶段的“下一项压力”必须能解释下一阶段的“新问题”；
- 如果无法建立具体连接，就合并、重排或删除该阶段；
- 抽象只能在学习者先遇到它所解决的压力之后引入。

### 5. 更新输出、校验与 fan-out 契约

- 输出树、模板、阅读顺序和课程完成门槛加入 `project-evolution.md`；
- 校验器要求 schema-v2 课程包含双语演变文档及新版里程碑标题；
- schema-v1 旧课程仍可使用旧里程碑格式，不被强制重置；
- fan-out planner 生成共享演变模型；
- consolidated render 同时负责核心文档、演变文档和 milestone definitions；
- 并行里程碑必须复用同一因果链。

## v2 的结果

v2 不只告诉学习者“下一步实现什么”，还要让学习者理解：

```text
为什么旧版本不再够用
为什么当前复杂度现在才值得引入
当前方案解决了什么
它又会制造什么新的设计压力
```

最终目标是训练学习者根据真实压力逐步增加复杂度，而不是背诵成熟仓库的最终结构。
